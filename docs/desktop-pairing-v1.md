# Multica 桌面端与本地服务器配对：后续阶段设计

本文记录 issue #3 后续阶段的现状边界和验收约束。它不是当前版本已实现的协议说明。

## 当前可复用的连接 seam

当前部署完成后已经能得到四类信息：

- 浏览器访问 origin；
- 目标主机服务间 origin；
- OAuth 回调 URL；
- 可选 Plane URL、Multica `/health` 和 `/readyz` 状态。

一体化 onboarding 还必须把用户登录和代码源连接分开处理：Gitea OAuth 适合内网自托管登录，GitHub Device Flow 适合本地桌面授权，GitHub App webhook 只有在公网 HTTPS origin 下才成立；GitHub、Gitea 或其他自托管 Git 的代码源选择和仓库授权仍属于 Multica 集成设置，不应通过桌面端下发长期 secret。

现有客户端引导流程接受一个自托管服务器 URL，先访问 `/health`，再调用官方 CLI 的 self-host 配置和浏览器登录，最后检查 `auth status` 与 `daemon status --output json`。这说明后续配对应优先复用健康检查、现有浏览器认证和官方 CLI/daemon，而不是让部署工具复制服务端长期密钥。

当前没有发现已存在的配对码、设备码、二维码、配对撤销或版本握手接口。部署工具也不会伪造这些接口。

## 建议的最小协议边界

后续实现前，应先由 Multica 服务端和桌面端共同确定版本化协议。推荐流程如下：

1. 桌面端输入或选择部署报告中的候选地址，依次执行 `/health` 和版本能力检查。
2. 桌面端请求开始配对；服务器创建不可预测的 pairing id、短时配对码和协议版本，并且只保存配对码哈希。
3. 服务器返回不含长期密钥的显示信息：候选地址、Multica 版本、Plane 状态和过期时间。桌面端展示配对码或二维码。
4. 用户在已登录的浏览器中确认设备。确认必须绑定 pairing id、目标用户、设备名和协议版本。
5. 服务器只允许一次消费短时 bootstrap credential。桌面端用它交换短期设备会话或官方 CLI 所需的最小授权结果。
6. 服务器返回非敏感运行配置和会话过期时间；长期应用密钥、数据库密钥、OAuth client secret、GitHub 私钥和 SSH 私钥永远不下发。
7. 桌面端立即用健康检查、认证状态和 daemon 状态完成验收，并显示具体失败阶段。

端点名称和载荷字段在协议评审前不应写死到部署工具。部署工具只需要消费已版本化的“配对入口/能力信息”，并把它接入部署完成报告。

## 凭证生命周期和撤销

- 配对码和 pairing id 应为高熵随机值；展示码不应直接作为长期凭据。
- bootstrap credential 应有短 TTL、单次消费、失败次数限制和服务端审计事件。
- 用户确认前可以取消；过期、成功交换或超过失败次数后立即失效。
- 已绑定设备应有可撤销的设备身份。撤销后，桌面端必须停止刷新会话并重新走完整配对。
- “重新配对”应先撤销旧设备会话，再生成新的 pairing id；不得复用旧码。
- 日志和部署报告只能记录脱敏的 pairing id 前缀、阶段和原因，不能记录配对码或 bootstrap credential。

## LAN、NetBird 与版本兼容

部署报告可以同时给出 LAN、NetBird 和域名 origin。桌面端应逐个检查候选地址，并明确显示“地址不可达”与“服务未启动”的区别；OAuth origin 仍以浏览器可访问地址为准。

配对请求必须包含协议版本、桌面端版本和能力集合。服务器应返回：支持、需要升级桌面端、需要升级服务器或不兼容。健康检查成功不能替代版本兼容检查。

## 验收测试

实现时至少需要覆盖：

- LAN 地址成功配对；
- NetBird 地址成功配对；
- 地址不可达、服务未启动；
- 配对码过期、重复消费、错误次数超限；
- 浏览器未登录、用户拒绝、认证失败；
- bootstrap credential 不出现在日志、配置导出或部署报告；
- 撤销后旧设备会话失效，重新配对生成新身份；
- 服务器/桌面端版本不兼容时给出可执行升级提示；
- 可选 Plane 状态只作为非敏感能力信息展示，不阻塞没有 Plane 的 Multica；
- 配对成功后，桌面端能读取服务地址、登录入口、版本和健康状态，并通过官方 CLI/daemon 完成最终连接检查。

在这些测试通过前，README 和安装器只能写“手动输入服务器 URL 并登录”，不能写“自动发现”或“一键配对”。
